# R3 — Обратная связь → подбор моделей по доменам на измеренном результате

ROLE: Senior data/ML engineer with strong PHP 8.5 and statistics literacy. Ты умеешь превращать журнал прогонов в измеримые оценки качества и не путаешь корреляцию с причиной.

## Контекст проекта

ReVoAp — self-hosted консенсус-движок (PHP 8.5, без фреймворка). Актуализация (`src/Models/ModelsActualizer.php`, задача `payload.kind = 'models_actualize'`) назначает пул моделей на каждый домен-пресет. Сейчас выбор опирается на **косвенные признаки**: семейство вендора (`src/Models/ProviderFamily.php`), «новее на линии» (`src/Models/ModelVersion.php`), reasoning-релиз, а также на анализатор (`src/Analyzer/RequestAnalyzer.php`).

## Что уже есть

- Пресеты: `domain_presets.definition_json` = `{models[], arbiter, skill_slug}`; пул доступен как `pipeline.default_selected_models`.
- Журнал: `council_steps` (статус, `summary`, `meta`: слой, модель, провайдер, `fallback_reason`, токены, `cache_*`), `council_model_responses` (ответ модели по каждому участнику), `pipeline_events` (события `L1_RESPONSE`, `L1_FAILED`, `L3_CONSENSUS`, `PIPELINE_DONE`).
- Статистика: `src/Stats/{StatsCollector,SessionStats,TokenUsage}.php`; в `PIPELINE_DONE.stats.per_layer` есть `cost`, `latency_ms`, `total_tokens`, `cached_tokens`.
- Актуализация уже пишет пресеты и связанные роли (analyzer/synthesis/arbiter) и проверяет инвариант «пул и роли ⊆ активный каталог».

## Цель

Пул на домен должен собираться по **измеренной отдаче** моделей, а метаданные вендора — оставаться фильтром кандидатов, а не решающим доводом. Оценки оператора должны в это входить.

## Объём работ

1. **Метрики по (модель × домен)** из журнала: доля успешных вызовов, участие в согласии, вклад в вердикт арбитра (влияние на итоговый ответ), медиана и хвост задержки, стоимость за тысячу токенов, попадания в кеш (`cache_discount`, токены кеша), частота отказов и повторов.
2. **Оценка оператора** — на финальном ответе и на ответе отдельной модели: полезно/бесполезно с причиной; хранится так, чтобы переживать новые прогоны и очистку кеша.
3. **Питание актуализации** — рейтинг кандидатов внутри домена: сначала фильтр (доступность, семейство, не batch-only), затем сортировка по измеренной отдаче с учётом минимального объёма выборки.
4. **Отчёт** — «модель × домен» с числами **и** объяснением, как это повлияло на состав пресета (какие кандидаты поднялись, какие ушли и почему).
5. **Деградация** — при малых выборках правило должно опускаться к текущему (метаданные), а не к случайному выбору; это должно быть видно в отчёте.

## Вне объёма

Публичный рейтинг моделей между пользователями, обучение собственной модели, изменение самой схемы консенсуса.

## Ограничения и конвенции репозитория

- Миграции: только новый файл `db/migrations/NNN_*.sql` по конвенции проекта (с `@table-version`), существующие колонки не менять; идемпотентность обязательна.
- PHP: `strict_types`, `final class`, PHPDoc; без новых Composer-зависимостей; git не трогать. JS: `el()`/`textContent`, `innerHTML` запрещён. CSS: только существующие токены.
- Не трогать `.dev_agent/**`, `archive/**`, `vendor/**`, `Consensus-AI-main/**`, `cache/**`, `logs/**`, `assets/js/copy_to_clipboard.js`, `deploy/host/**`.
- Никаких «чёрных ящиков»: любое влияние на состав пула должно быть объяснимо текстом в отчёте.

## Критерии приёмки

- Есть отчёт «модель × домен» с числами и указанием объёма выборки.
- Видно, как измеренные данные изменили состав пресета относительно метаданных.
- Оценки оператора сохраняются и учитываются; их отсутствие не ломает подбор.
- При малой выборке правило опускается к текущему поведению и говорит об этом.
