# R14 — Массовый сценарий на пакетном контуре: список вопросов → таблица результатов

ROLE: Senior backend engineer specialised in batch and asynchronous pipelines, with data-ingestion rigour (PHP 8.5) and enough frontend skill to present a results table honestly.

## Контекст проекта

ReVoAp — self-hosted консенсус-движок. Пакетный контур уже реализован: загрузка JSONL, создание пакета, опрос, приём результатов по `custom_id`, отмена, состояние задачи переживает перезапуск воркера. Но он умеет **один** прогон, тогда как его смысл — дешёвая асинхронная обработка **многих** задач.

## Что уже есть

- `src/Connectors/Batch/*` (клиент: файлы, пакеты, статус, отмена, список, скачивание, список batch-способных моделей; подменяемый транспорт), `src/Batch/*` (`BatchState`, `BatchPipeline`, `BatchCanceller`, `BatchCapability`, `BatchCustomId`, `BatchJsonlBuilder`, `BatchResultParser`).
- Задача `payload.kind = 'batch_pipeline'` в воркере: фазы, парковка по `next_run_at`, частота опроса (30 с до 1000 строк, 150 с для крупных), состояние в `result_json`, отмена.
- Режим «Run via Batch API» для прогона из чата (`run_mode = 'batch'`), карточка жизненного цикла, состояние «ожидает пакет» в History.
- Признак batch-only у моделей (`src/Models/ModelId.php`), готовность контура в boot-config.
- История: `council_sessions`, `council_steps`, `council_model_responses`.

## Цель

Оператор загружает список вопросов и получает таблицу результатов: вопрос, статус, ответ, стоимость; неудачи — отдельным списком с причинами. Без ручных действий на каждый вопрос.

## Объём работ

1. **Загрузка списка** — текстовый файл (по одному вопросу на строку) или JSONL; локальная валидация до отправки (пустые строки, дубликаты, слишком длинные, лимит размера) с понятным отчётом; ничего не отправлять, пока список не принят.
2. **Разбиение на пакеты** — с учётом лимитов провайдера и рекомендаций опроса (до 1000 строк — 30 с; крупнее — 2–5 минут); несколько пакетов могут идти параллельно, если это безопасно, иначе последовательно — решение обосновать.
3. **Прослеживаемость** — каждая строка списка связана со своим `custom_id` и, значит, с шагом и ответом в журнале; строки, для которых ответ не пришёл, перечисляются поимённо (это уже требование построителя и разборщика — не ослаблять).
4. **Таблица результатов** — вопрос, статус, ответ, стоимость, время; выгрузка в Markdown/CSV; фильтр «только неудачи»; переход к прогону в History.
5. **Отмены и сбои** — отмена массового задания отменяет незавершённые пакеты у провайдера (за уже отработанное списываются деньги — это должно быть сказано); при частичном сбое успешные строки сохраняются.
6. **Уведомление** — по завершении массового задания уведомить оператора (перекликается с R-6), потому что ожидание измеряется часами.

## Вне объёма

Собственный веб-интерфейс загрузки больших файлов через внешние хранилища, оценочные прогоны нескольких конфигураций (A/B — отдельный пункт).

## Ограничения и конвенции репозитория

- PHP: `strict_types`, `final class`, PHPDoc; без новых Composer-зависимостей; git не трогать. JS: `el()`/`textContent`, `innerHTML` запрещён. CSS: только существующие токены.
- Миграции — только новый файл `db/migrations/NNN_*.sql` с `@table-version`, идемпотентно.
- Не трогать `.dev_agent/**`, `archive/**`, `vendor/**`, `Consensus-AI-main/**`, `cache/**`, `logs/**`, `assets/js/copy_to_clipboard.js`, `deploy/host/**`.
- В среде разработки у PHP нет ext-curl — все проверки клиента идут на фикстурном транспорте; это надо честно указывать.
- Состояние массового задания обязано переживать перезапуск воркера (существующая парковка) — не изобретать второй механизм.

## Критерии приёмки

- Список из N вопросов доходит до результата без ручных действий на каждый вопрос.
- Частичные отказы видны построчно, с причиной; успешные строки не теряются.
- Отмена останавливает незавершённые пакеты и объясняет последствия расхода.
- Состояние переживает перезапуск воркера.
