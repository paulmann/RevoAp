# ROAD_MAP - RevoAp: план развития продукта

> Версия: 1.1.0 · Дата: 2026-09-27 · Статус: рабочий документ (обновляется по факту работ)
> Проект: RevoAp (бывш. OpenCorum), PHP 8.4-совместимый исходник, проверенный рантайм PHP 8.5 CLI
> Формат документа: сводная таблица приоритетов + на каждый пункт секции Зачем / Текущее состояние / Решение / Компоненты / Готовность / Риски

## Принципы приоритизации

- **P0** - максимум пользы на единицу усилий: короткие, автономные улучшения пользовательского опыта и надёжности; делаем первыми.
- **P1** - высокая ценность, умеренные усилия: сервисные возможности (автовыбор, бюджеты, здоровье моделей, кэш, метрики качества).
- **P2** - стратегические: исследовательские и продуктовые расширения (arxiv, A/B, версионирование, экспорт/импорт, стриминг, внешний API).
- **P3** - гигиена: документация, сценарные тесты, целевая версия PHP, i18n/доступность.

Критерий попадания в P0: эффект очевиден пользователю немедленно И стоимость низкая/средняя И риск низкий.

## P0 - первые к реализации

## P0-1 · Наглядный прогресс выполнения: номер шага N/M и % выполнения

**Зачем.** Сейчас статус прогона читается как лента событий, но пользователь не видит целого: сколько уже сделано и сколько осталось. Нужен вывод процесса в духе AutoClaw Z-code - с номером шага (N/M) и процентом выполнения - при этом сохранить информативность (карточки шагов, бейджи, статистика остаются).

**Текущее состояние.** UI пайплайна реализован в assets/js/pipeline.js: карточки шагов добавляются append-only, слои L0-L4 получают бейджи и tooltips (LAYER_TOOLTIPS/EVENT_TOOLTIPS), внизу закреплена карточка «Current activity», текст которой собирает humanActivityLabel(type, payload). Сквозного номера шага, общего количества и процента выполнения НЕТ. Пайплайн динамический: число L1-вызовов зависит от ролей и выбранных моделей, циклы консенсуса ограничены cycle_limit (1..5) и loop-guard'ами, поэтому точный итог заранее неизвестен.

**Решение.** Двухуровневый прогресс.
1. Нумерация шагов: движок эмитит в событиях поля step_index и step_total_estimate (на основе фактически запланированных L1-вызовов: роли × выбранные модели + L2 + L3 + L4). Оценка корректируется, если пайплайн допланирует циклы консенсуса. UI показывает «Шаг 4/9» в заголовке каждой карточки и в Current activity («Шаг 4/9 · L1 - вызов модели …»).
2. Процент выполнения: взвешенные вехи слоёв (L0 - 5%, L1 - 40%, L2 - 15%, L3 - 15%, L4 - 25%), внутри L1 - равномерно по моделям; при циклах консенсуса вес циклов распределяется заранее по cycle_limit. Прогресс-бар выводится в шапке пайплайна, проценты - в Current activity.
3. Дополнительно: оценка оставшегося времени (ETA) по средним латентностям из статистики (см. P1-6), если данных достаточно; иначе скрыта.

Информативность сохраняется: существующие карточки, бейджи L0-L4 и вкладки статистики не меняются - добавляется только слой прогресса.

**Компоненты.** src/Pipeline/PipelineEvent.php (новые поля), src/Pipeline/PipelineEngine.php (расчёт и эмит вех), src/Pipeline/SseEventStreamer.php, assets/js/pipeline.js (прогресс-бар, бейдж N/M, ETA), assets/js/app.js.

**Готовность.** Unit: расчёт весов и N/M на фиктивных событиях; сценарий: прогон с 2 моделями → UI показывает шаги 1..N и монотонно растущий процент до 100% на PIPELINE_DONE; SmokeTest-ассерты на новые поля событий.

**Риски.** Динамический характер пайплайна (циклы, guard'ы) - итоговое N может меняться; решается «оценочным N» с корректировкой, а не жёстко фиксированным числом. Регрессии DOM - append-only контракт сохраняется.

## P0-2 · Автоподмена упавшей модели из списка потенциальных (auto-fallback)

**Зачем.** Одна не отвечающая модель не должна ронять прогон. Пользователь просит галочку, разрешающую автоматически подставить следующую модель из списка потенциальных, если какая-либо модель не ответила.

**Текущее состояние.** В каждом пресете модели уже размечены флагами selected/active: selected=true участвуют в прогоне, selected=false - «потенциальные» кандидаты (так построены canonicalPresets в src/DomainPresets/DomainPresetRepository.php; selectedModels() берёт только выбранные). ParallelChatDispatcher возвращает на каждый запрос строку {ok: false, error}: при сбое модели PipelineEngine эмитит L1_FAILED; если упали все выбранные - L1_NO_AVAILABLE_MODELS / L1_NO_RESULTS, и прогон завершается без финального ответа. Механизма подстановки из потенциальных моделей НЕТ.

**Решение.**
1. Новая опция пресета auto_fallback: bool - галочка в Settings → Domain Models (на каждый пресет) + глобальный дефолт в config.php.
2. В PipelineEngine при L1_FAILED для конкретной пары (provider, model) выбирается кандидат из пула пресета с selected=false и active=true. Приоритет выбора: (а) тот же провайдер; (б) та же «семья» модели (совпадение по префиксу slug); (в) лучший health-скор (см. P1-6, когда реализован; иначе по порядку в списке).
3. Защиты: max_fallbacks_per_step (по умолчанию 1 на модельный слот), исключение уже упавших моделей из кандидатов, учёт бюджета (P1-5), арбитр по умолчанию не подменяется (строгая опция включается отдельно).
4. Аудит: новое событие L1_FALLBACK с полями original/replacement/reason; карточка шага получает бейдж «fallback: A → B»; замена фиксируется в council_steps.

**Компоненты.** src/Pipeline/PipelineEngine.php, src/DomainPresets/DomainPreset.php (поле auto_fallback), src/DomainPresets/DomainPresetRepository.php, src/Http/Controllers/DomainPresetsController.php, db/schema.sql (миграция колонки), assets/js/pipeline.js (бейдж + tooltip), assets/js/settings.js (галочка).

**Готовность.** Unit: выбор кандидата (приоритет провайдер → семья → health, исключения, пул исчерпан); сценарий: модель A падает → вызывается B из потенциальных → финальный ответ собран; прогон без галочки ведёт себя как раньше.

**Риски.** Качество ответа замены непредсказуемо - сглаживается health-скором и видимым бейджем; рост стоимости прогона - лимит подмен на слот и бюджет; зацикливание - исключение неудавшихся моделей и счётчик подмен.

## P0-3 · Автообновление версий моделей по кнопке

**Зачем.** Провайдеры (OpenRouter и др.) постоянно обновляют каталог; выбранные модели устаревают. Нужна одна кнопка в настройках: обновить список моделей И разом перераспределить актуальные версии по всем типам консенсуса (всем пресетам, включая арбитра и модели синтеза), а не только загрузить новый список.

**Текущее состояние.** Каталог моделей статичен: modelCatalog() в src/Http/Controllers/DomainPresetsController.php читает Config::get('models'); живого фетча с провайдера нет. Apply (v1.8.41) умеет лишь пере-распределять выборки по одному выбранному провайдеру внутри уже существующего списка. Версии захардкожены в canonicalPresets (например arbiter openai/gpt-5.5, default-арбитр openai/gpt-5.5-pro) и в config.php (pipeline.synthesis_model).

**Решение.**
1. Новый сервис ModelVersionService: фетч GET https://openrouter.ai/api/v1/models (с имеющимся API-ключом провайдера), кэширование ответа (TTL 1 час, диск в runtime/).
2. Маппинг устаревших id на актуальные: нормализация slug + «семейный» матч (openai/gpt-5.5* → последний релиз в семействе) + таблица ручных алиасов в config.php.
3. Endpoint POST /api/domain-presets/refresh-versions (admin-gated через существующий guard()): строит diff-превью по ВСЕМ пресетам (каждая строка моделей + arbiter) и по config-ключам синтеза; возвращает planned changes, ничего не применяя.
4. Кнопка «Обновить версии моделей» в Domain Models: модал с diff (старый → новый), подтверждение → apply: сохранение каждого пресета через DomainPresetRepository::save и обновление synthesis_model через ConfigRepository. Перед apply - бэкап (snapshot + версия ConfigRepository); откат по кнопке из истории.
5. Распределение по всем типам консенсуса гарантируется тем, что сервис итерирует ВСЕ пресеты (системные default/mathematics/physics + пользовательские) и arbiter-роли, а не один выбранный пресет.

**Компоненты.** новый src/Settings/ModelVersionService.php, src/Http/Controllers/DomainPresetsController.php, src/DomainPresets/DomainPresetRepository.php, src/Settings/ConfigRepository.php, config.php (таблица алиасов, TTL), assets/js/settings.js (кнопка + модал diff).

**Готовность.** Unit: маппинг slug-семей на фикстурном каталоге JSON (без сети), diff-билдер, откат восстанавливает пресеты; сценарий: каталог содержит gpt-5.5-pro как замену gpt-5.5 → кнопка показывает diff по всем трём системным пресетам и арбитрам → после apply все пресеты на актуальных версиях; ручная QA с живым ключом.

**Риски.** Переименования моделей без 1:1 маппинга (семейный матч + ручные алиасы + превью перед apply); сетевые сбои фетча (кэш и грациозная деградация); случайная поломка рабочей конфигурации (diff-превью + история отката).

## P1-4 · Автовыбор консенсуса под задачу + генерация ролей и системного промпта

**Зачем.** Пользователь не должен сам выбирать пресет и роли: система сама определяет тип консенсуса по задаче и строит под неё лучший состав ролей и системного промпта.

**Текущее состояние.** DomainRouter классифицирует запрос ключевой эвристикой только в три захардкоженных пресета (default/mathematics/physics), с риском ложных срабатываний у хвостовых слов. SkillAutoCreator умеет LLM-генерацию ролей, но только для skills (JSON-определения), не для Domain Presets. Сборка итогового системного промпта происходит в SystemPromptAssembler, но без связи с пресетами.

**Решение.** Двухэтапный автовыбор.
1. Классификатор расширяется: помимо keyword-эвристики вводится LLM-классификатор (дёшево, 1 короткий вызов) поверх эвристического префильтра. Результат - тег домена + уверенность.
2. Выбор пресета: если уверенность высокая и подходящий пресет существует - сразу выбирается. Если пресета нет - запускается генерация DomainPreset (аналог SkillAutoCreator::draftDefinition, но на DomainPreset-структуру): роли {key,label,system} генерируются под задачу, системный промпт ролей и synthesis_prompt собираются через SystemPromptAssembler.
3. Сгенерированный пресет показывается пользователю на превью (роли + промпт + модели из default-пула) до начала прогона с кнопками «Использовать сразу» и «Сохранить как пресет».
4. Выбор моделей для сгенерированного пресета - из default-пула, с учётом статистики здоровья моделей (P1-6, когда реализован).

**Компоненты.** src/DomainPresets/DomainRouter.php, src/Profiles/SystemPromptAssembler.php, src/Skills/SkillAutoCreator.php (обобщить LLM-draft), новый src/DomainPresets/DomainPresetGenerator.php, src/Http/Controllers/DomainPresetsController.php, assets/js/settings.js (превью-модал).

**Готовность.** Unit: LLM-классификатор на фикстурах (без сети), генератор пресетов (валидация ролей, slug), превью-проекция. Сценарий: запрос про квантовую физику → пресет physics без ручного выбора; запрос вне трёх пресетов → превью нового пресета → «Использовать сразу» → прогон с его ролями.

**Риски.** Стоимость дополнительного LLM-вызова классификации (короткий, дешёвый вызов; кэшируется); плохие генерации ролей (жёсткая валидация структуры и превью-гейт); размытие границы skill-vs-preset (единый контракт ролей в обеих сущностях).

## P1-5 · Бюджеты и лимиты прогонов

**Зачем.** Непредсказуемая стоимость прогона - главный барьер доверия к авто-фичам (P0-2, P1-4): пользователь должен видеть оценку до запуска и жёсткие лимиты во время прогона.

**Текущее состояние.** Уже есть per-вызов статистика стоимости (ChatResponse::statsPayload), TokenUsage::estimateTokens и StatsCollector; дневных лимитов и предпросмотра стоимости нет.

**Решение.**
1. Предпросмотр стоимости до запуска: оценка токенов запроса через TokenUsage, твёрдые цены из каталога моделей (расширение ModelVersionService, P0-3), итог в UI под формой запроса.
2. Лимиты: daily_budget (сумма через статистику за день), per_run_budget, monthly_budget в config.php; движок проверяет перед каждым платным блоком и завершает прогон с событием BUDGET_EXCEEDED.
3. UI: прогресс бюджета в шапке прогона, предупреждение при достижении 80%.

**Компоненты.** src/Stats/TokenUsage.php, src/Statistics/StatisticsService.php (агрегация за период), src/Pipeline/PipelineEngine.php (проверки), config.php (лимиты), assets/js/app.js (предпросмотр и прогресс), src/Settings/ModelVersionService.php (цены).

**Готовность.** Unit: оценка стоимости на фикстурах, проверка лимитов; сценарий: лимит 0.01 → прогон завершается BUDGET_EXCEEDED с понятным сообщением.

**Риски.** Неточность оценки (эстимейт помечается как «estimated»); ложное срабатывание лимитов (пороги настраиваются, событие показывает фактическое превышение).

## P1-6 · Мониторинг здоровья моделей

**Зачем.** Мало знать, что модель есть в каталоге, нужно знать, как она реально отвечает; иначе автовыбор (P1-4), автоподмена (P0-2) и обновление версий (P0-3) слепы.

**Текущее состояние.** Статистика по моделям накапливается в council_steps/статистике прогонов (StatsCollector, StatisticsService, ChatResponse::statsPayload), но агрегированного health-индекса нет.

**Решение.**
1. Health-индекс модели: скользящее окно (последние 30 дней) по успешности (ok / total), медианной латентности, ошибкам по типу (429, 5xx, timeout) и стоимости за токен.
2. Бейджи в Domain Models: зелёный (healthy), жёлтый (деградация), серый (нет данных).
3. Автоотключение: при health ниже порога модель снимается с выбора и попадает в «потенциальные» с пометкой; ручная переустановка через UI.
4. Потребители: выбор кандидатов в P0-2 и P1-4, маппинг в P0-3.

**Компоненты.** новый src/Statistics/ModelHealthService.php, src/Statistics/StatisticsService.php, src/Http/Controllers/DomainPresetsController.php, assets/js/settings.js (бейджи), db/schema.sql (кэш-таблица индекса).

**Готовность.** Unit: расчёт индекса по фикстурной статистике, пороги; сценарий: модель с 90% ошибок → бейдж красный и автоотключение; после серии успехов бейдж снова зелёный.

**Риски.** Флуктуации на малой выборке (минимум ответов для оценки); автоотключение хорошей модели после разового сбоя (требует серии сбоев, не одного).

## P1-7 · Кэш ответов и офлайн-деградация

**Зачем.** Идентичные или пересекающиеся запросы не должны платить полную стоимость; при полном отказе всех провайдеров пользователь должен получить last-known-good ответ, а не пустоту.

**Текущее состояние.** Кэширование встроено неявно: ModelResponseCache в src/Cache кэширует ответы LLM в cache/*.json, а AbstractConnector ретраит 429/5xx. Режима last-known-good при недоступности всех моделей нет.

**Решение.**
1. Явная политика кэша: TTL и объём кэша в config.php, инвалидация при изменении модели/пресета.
2. Reuse-кэш: хэш (роль, модель, системный промпт, тема запроса дословно) → готовый ответ без повторного вызова.
3. Офлайн-деградация: если все выбранные модели недоступны, ищется ответ из кэша на похожий промпт (семантически по нормализованному тексту), результат помечается как cached/degraded с бейджем предупреждения и без перезапуска цикла.

**Компоненты.** src/Cache/ModelResponseCache.php, src/Pipeline/PipelineEngine.php, src/Connectors/ParallelChatDispatcher.php, assets/js/pipeline.js (бейдж degraded).

**Готовность.** Unit: хэш-инварианты (порядок ролей/пробелы), инвалидация; сценарий: у всех провайдеров нет ключа → прогон завершается cached-ответом с предупреждением, не пустым экраном.

**Риски.** Устаревшие ответы (пометка degraded и запрет кэша при auto_fallback подменах); рост диска (лимит объёма и LRU-вытеснение).

## P1-8 · Метрики качества консенсуса

**Зачем.** Пользователь видит verdict и score, но не понимает, насколько хорош сам консенсус. Нужна самодиагностика механизма.

**Текущее состояние.** SemanticConsensusEngine считает Jaccard-сходство и agreement/partial/conflict, ConsensusExplainer объясняет вердикт; агрегированной метрики качества механизма нет.

**Решение.**
1. Метрики: средний score по типам пресетов, доля conflict, среднее число пар и циклов до консенсуса, доля ответов, пришедших из fallback (P0-2) или кэша (P1-7).
2. Автонастройка порога арбитра: если конфликтные случаи систематически уходят в арбитра, а его решение совпадает с большинством - порог можно снизить, и наоборот.
3. Панель качества в статистике: тренды по дням.

**Компоненты.** src/Consensus/SemanticConsensusEngine.php, src/Consensus/ConsensusExplainer.php, src/Statistics/StatisticsService.php, assets/js/statistics.js.

**Готовность.** Unit: расчёт метрик на фикстурных вердиктах; сценарий: серия прогонов с искусственными конфликтами → панель показывает рост доли conflict и рекомендацию по порогу.

**Риски.** Автонастройка порога по шумным данным (минимальная выборка перед рекомендацией, применяется только с подтверждением).

## P2-9 · Исследователь улучшений по arxiv + генерация новых консенсусов

**Зачем.** Продукт основан на методах из научных работ; пользователь просит кнопку, которая сама ищет свежие публикации по arxiv, анализирует их и предлагает новые консенсусы.

**Текущее состояние.** arxiv присутствует только как ссылки: докблок SemanticConsensusEngine перечисляет четыре работы (arXiv 2601.07245, 2504.02128, 2411.06535, 2312.07622), а docs/consensus-research.md их анализирует. Автоматизированного поиска и анализа нет.

**Решение.**
1. ArxivSearcher: запросы к arxiv.org/api/query (Atom XML) по темам (multi-agent LLM, consensus, ensemble, reasoning) с фильтром по дате; парсер в PHP.
2. LLM-анализ: для каждой найденной работы модель пишет summary + релевантность к движку + идеи для улучшений.
3. Генерация консенсуса: из выбранной работы генерируется проект DomainPreset (роли, системные промпты, параметры порогов) по контракту из P1-4; превью в UI, сохранение по кнопке.

**Компоненты.** новый src/Settings/ArxivSearcher.php, src/DomainPresets/DomainPresetGenerator.php (P1-4), src/Http/Controllers/DomainPresetsController.php, assets/js/settings.js (вкладка Research), config.php (ток-темы и лимиты).

**Готовность.** Unit: парсер Atom на фикстурах, валидация проектов; сценарий: фикстурный Atom-фид → отчёт с работами → генерация пресета → сохранение; ручная QA с живым arxiv.

**Риски.** Шум нерелевантных работ (фильтр + LLM-рейтинг); API-лимиты arxiv (задержка между запросами, кэш); юридическая корректность использования текстов работ (работаем с метаданными и саммари, не пересылаем полные тексты).

## P2-14 · Внешний API для запуска консенсуса

**Зачем.** Интеграция с внешними системами: запуск прогона, чтение статуса и результата.

**Статус: реализовано (v1.8.43).** Полный референс: [`docs/api-rest.md`](docs/api-rest.md).

**Решение (реализованное).** REST API под `/v1/*`: собственные API-ключи `rv_*` (SHA-256-хранение, scopes full/read, rpm/daily-квоты), аутентификация и rate-limit (ApiAuth, дени-лист операторских путей, per-IP бюджет 120 req/min), адаптер форматов (native/OpenAI/Anthropic ↔ внутренний payload), `POST /v1/runs` в трёх режимах (async 202, sync, SSE-стрим), чтение (`/v1/runs`, `/{id}`, `/{id}/events`, `/{id}/result`, `/{id}/cancel`, `/models`, `/usage`), вебхуки `run.completed|failed|cancelled` с HMAC-подписью и повторами. **Готовность.** Unit-тесты ключей/авторизации/адаптера/запуска/чтения/вебхуков/безопасности (322 ассерта), сценарные тесты в `tests/scenarios/ApiScenariosTest.php`.

**Риски.** Безопасность ключей закрыта: только SHA-256-хеши в БД, fail-closed IP-счётчики, аудит без секретов. Возможное развитие: версионирование API (v2), scoped-keys на конкретные run'ы, метрики качества через API.

## R-1 — Прозрачность прогона до отправки: участники, арбитр, оценка стоимости и времени

**Статус.** ✅ **Реализовано 23.09.2026.**

Что сделано:

1. **Состав и арбитр в карточке вопроса** — под задачей видно участников и модель-арбитра; состав сначала «как запрошено», затем заменяется на «как разрешил сервер», а при расхождении называются выпавшие модели и причины.
2. **Оценка стоимости и времени до запуска** — из истории по пулу предстоящего прогона: диапазон стоимости, ожидаемое время, объём выборки; при отсутствии истории так и сказано, а не показан ноль.
3. **Факт после прогона** — в том же блоке строка «Ran: …»: стоимость (или «провайдер не сообщил»), токены и сколько из них обслужено кешем.
4. **Потолок стоимости** — настройка `economy.budget_per_run`, вердикт `{limit, estimated_high, exceeded, note}` в совете и предупреждение в карточке.
5. **Честность при отсутствии данных** — «оценки нет», «цена не сообщена», «кеш не измерялся» вместо нулей; ошибка загрузки совета показывается как недоступность, а не как «всё хорошо».

Точки входа: `renderQueryCard(query, info)` и `updateQueryEconomy`/`updateQueryEconomyResult` в `assets/js/pipeline.js`, `arbiter`/`arbiter_source` в событии `L0_OPTIONS` (`PipelineEngine`), `POST /api/council/economy/advice`.

**Отклонение, о котором надо знать.** Потолок **предупреждает**, а не запрещает: оценка приходит уже после отправки, поэтому настоящий запрет требует гейта до запуска (совет → подтверждение → запуск) — это отдельное решение о продукте, а не деталь. Сейчас приложение сообщает факт превышения и называет выход.

Проверено: харнесс `tests/harness/chat-stream.mjs` (154/0), `tests/EconomyPolicyTest.php` (53/0 — включая потолок), `tests/ChatStreamDomTest.php` (8/0), `SmokeTest` 1534/54 без роста; живая проверка `L0_OPTIONS`, boot-config и `economy/advice` на боевом сервере.

**Проблема.** Оператор отправляет задание, не зная ни состава участников, ни модели-арбитра, ни
порядка цены и времени. Фактическая стоимость и задержка видны только в статистике **после** прогона
(`PIPELINE_DONE.stats.per_layer`), а прогон с восемью моделями и несколькими раундами может стоить
заметно и идти минуты.

**Решение.**
1. Под задачей в чате показывать состав: участники, арбитр (с ролью), выбранный совет и домен.
2. Оценка до отправки: диапазон стоимости и времени по истории для этого набора моделей и похожего
   объёма промпта, с явной пометкой «оценка».
3. Необязательный потолок на прогон: превышение — предупреждение с возможностью продолжить или
   уменьшить пул.

**Затронуто.** `assets/js/pipeline.js` (карточка задачи), `assets/js/app.js`, `src/Statistics/*`,
`src/Pipeline/PipelineEngine.php` (состав и арбитр в раннем событии), Help.

**Критерии приёмки.** До отправки видны участники, арбитр и оценка; состав, подтверждённый сервером,
совпадает с показанным (или расхождение объяснено); при превышении потолка прогон не стартует без
подтверждения.

**Риск.** Оценка по истории неточна на новых моделях — поэтому она и подписывается как оценка, а не
как факт.

## R-2 — Один экран «что случилось и что нажать»: диагностика прогона с действиями

**Статус.** ✅ **Реализовано 23.09.2026.**

Что сделано:

1. **Классификатор причин** — `src/Diagnostics/RunDiagnosis.php`, чистый, 12 классов: устаревший код воркера, отставание схемы, пустой разрешённый пул, провал синтеза, отсутствие ответов L1, недоступный коннектор, модель, которую провайдер больше не обслуживает, batch-only идентификатор, разомкнутые размыкателем модели, «запись говорит completed, а шаг упал», плюс честный запасной вариант «причина не записана». **Системные причины проверяются раньше причин прогона** — и это подтвердилось на живых данных: у сессий #21 и #22 диагноз сразу указал на схему, а не на их собственные симптомы.
2. **У каждой причины есть действие** — проверяется отдельным тестом, который обходит все классы: вердикт без действия невозможен, кроме успешного.
3. **Панель в детали прогона** — первой, до доказательств: причина, объяснение человеческим языком и кнопки.
4. **Действия трёх видов** — и различие осознанное: `endpoint` — кнопка вызова уже существующего эндпоинта (применение миграций, обновление каталога, повтор синтеза), причём меняющие состояние требуют **второго клика** подтверждения; `navigate` — кнопка, открывающая нужный экран (Settings); `command` — текст с командой. Перезапуск сервиса остаётся **действием оператора**: приложение не выполняет `systemctl` само.
5. **После действия деталь перечитывается** — оператор видит новое состояние, а не оптимистичное сообщение; ошибка показывается текстом от сервера.
6. **Системные факты подключены** — версия, которую сообщил работающий воркер, против выложенной, и версия схемы в `app_config` против объявленной в `db/schema.sql`; чтение защищено, неудача оставляет «неизвестно», а не ломает деталь.

Живая проверка (сессии #21 и #22 на боевом): `cause=schema_out_of_date`, «The database schema is behind: live 1.8.44, expected 1.9.0», действия `Apply migrations [endpoint]` и `Open the raw record [navigate]`.

**Перезапуск воркера из панели** сделан без единой привилегии: панель **не** перезапускает systemd-юнит (для этого понадобился бы sudo, а это решение другого масштаба) — она записывает метку времени, воркер сравнивает её **со своим временем старта** и при более новой метке завершается штатно, а `Restart=always` поднимает свежий процесс уже на выложенном коде. Метка — именно время, а не флаг: иначе одно нажатие превратило бы кнопку в выключатель. Проверено на боевом: `POST /api/worker/restart` → в журнале `worker.restart_requested` → через 6 секунд `worker.start` с новым PID и версией 1.9.0.

Проверено: `tests/RunDiagnosisTest.php` (23/0), `tests/WorkerRestartSignalTest.php` (9/0), `tests/HistoryCompletionTest.php` (110/0), `SmokeTest` 1534/54 без роста; перезапуск воркера подтверждён журналом боевого сервера. Кнопки в панели автотестом не покрыты — харнесса для `history.js` в проекте нет.

**Проблема.** При сбое оператор видит статус, но не причину и не следующий шаг: отклонённые модели,
недостижимый провайдер, мёртвая модель синтеза, устаревший код воркера и неприменённая миграция —
разные по сути отказы с одним и тем же «Error».

**Решение.** Один блок диагностики прогона: терминальная причина человеческим языком, отклонённые
записи с причинами, что именно проверялось предполётно, и кнопки действий — «заменить модель»,
«повторить синтез», «обновить каталог», «применить миграции», «перезапустить воркер» (последнее —
безопасно только если юнит объявляет авто-перезапуск).

**Затронуто.** `src/Pipeline/PipelineEngine.php`, `src/Jobs/*`, `src/History/*`, `assets/js/history.js`,
`assets/js/pipeline.js`, `index.php`.

**Критерии приёмки.** Для каждого класса отказа из истории есть причина и хотя бы одно действие;
после действия состояние перепроверяется и результат показывается честно.

**Риск.** Действия меняют состояние — каждое должно быть идемпотентным и подтверждаемым.

## R-3 — Обратная связь → самообучающийся подбор моделей по доменам

2. Добавить оценку оператора (полезно/бесполезно с причиной) на финальном ответе и на ответе модели.
3. Питать этим актуализацию: пул на домен собирать по измеренной отдаче, а метаданные вендора
   оставить фильтром кандидатов, а не решающим доводом.

**Затронуто.** `src/Models/ModelsActualizer.php`, `src/History/*`, `src/Stats/*`, `db/schema.sql`
(оценки и агрегаты), `assets/js/history.js`.

**Критерии приёмки.** Есть отчёт «модель × домен» с числами, и видно, как он повлиял на состав
пресета; оценки оператора переживают новые прогоны.

**Риск.** Мало данных на старте — решение должно деградировать к текущему правилу, а не к случайному.

**Риск.** Дубли уведомлений при переподнятии задачи — нужен идемпотентный признак «уже сообщили».

## R-7 — Панель здоровья системы с починкой в один клик

**Проблема.** Класс сбоев, который уже стоил больше всего времени: воркер работает старым кодом,
миграция не применена, права на файлы сбиты, каталог устарел, пул расходится с каталогом. Каждый
раз это выясняется руками.

**Решение.** Один экран: версия кода воркера против выложенного кода, состояние миграций и версии
схемы, права на записываемые каталоги, свежесть каталога, инвариант «пул и роли ⊆ активный каталог»,
переподключения к БД — и рядом конкретное действие для каждого пункта. Плюс компактный чек-лист
первого запуска для новой установки.

**Затронуто.** `src/Jobs/WorkerHealthService.php`, `src/Settings/*`, `src/Http/Controllers/*`,
`assets/js/settings.js`, Help.

**Критерии приёмки.** Каждая проверка объясняет, что не так и что нажать; после починки состояние
перечитывается и показывается результат.

**Риск.** «Одна кнопка» на боевой системе требует подтверждения и журналирования.

**Статус.** ✅ **Реализовано 24.09.2026.**

Пункт закрыт как одна читаемая страница, а не как набор индикаторов: каждая проверка объясняет, что именно
не так, и предлагает конкретное действие; после действия состояние **перечитывается** и рядом с проверкой
печатается новый вердикт («State re-read at …» — видно, что стало, а не что «должно было стать»).

Что сделано:

1. **Только чтение.** `GET /api/health/system` (`src/Http/Controllers/SystemHealthController.php` →
   `src/Settings/SystemHealthService.php` → чистый `src/Diagnostics/SystemHealth.php`) собирает факты теми же
   сервисами, что уже владеют ими: `WorkerHealthService` (версия кода воркера, переподключения к БД),
   `ConfigRepository` + `MigrationManager` + `VersionParser` (схема и миграции), `StorageProbe` (права),
   каталог моделей и `LinkedModels` / `DomainPresetRepository` (инвариант пула). DDL не выполняется:
   `ModelsSnapshotStore::available()` и `ConfigRepository::ensureTable()` создают таблицы, поэтому не
   вызываются — снимок читается через `get()`. Эндпоинт публичный (как остальные `/api/health/*`): чек-лист
   первого запуска должен читаться до появления админ-ключа.
2. **Шесть проверок:** версия кода воркера против выложенного (`code_state`), миграции и версия схемы, права
   на записываемые каталоги (`var/config`, `runtime`, `cache`, `logs`), свежесть каталога моделей, инвариант
   «пул, пресеты и роли ⊆ активный каталог», переподключения к БД. Проверка без действия не выпускается:
   «не удалось посмотреть» тоже предлагает кнопку «Re-check now».
3. **Починка — существующими эндпоинтами.** Действия ведут на уже гейтенные `POST /api/settings/migrations/apply`,

## R-9 — Досье моделей

**Статус.** ✅ **Реализовано 23.09.2026.**

Что сделано:

1. **Вклад каждой модели в решение.** Движок консенсуса считал попарное сходство, но наружу отдавал только общий балл; теперь он отдаёт разбивку по участникам. Вклад = доля того, что сказала модель, подтверждённая **остальными**, и её доля в общем объёме подтверждённого. Это доля согласия, а не объёма: многословная модель, которую никто не подтвердил, получает мало.
2. **Показ под финальным ответом** — строка с процентами по каждой ответившей модели; формулировка называет меру, чтобы процент не читался как оценка качества; при отсутствии подтверждений строки нет.
3. **Накопление полезности** — `src/Models/ModelUsefulness.php`: по каждой модели раунды участия, средняя доля, и раздельно `strongly` (большая часть ответа подтверждена), `weakly` (почти ничего) и `neutral`. Именованный вклад записывается в шаг L3 каждого раунда, поэтому копится сам.
4. **Неответы отделены** — таймауты, 429, 5xx, обрыв, отказ по ключу и размыкание попадают в **отдельный счётчик с причиной** и никогда в отрицательную полезность. Проверено на живых данных: две модели с реальными таймаутами дали `weakly = 0` и `not answered = 2` с причинами.
5. **Метрики модели** — `src/Models/ModelMetrics.php`: медиана и хвост (p95, nearest-rank) по вызовам, которые действительно ходили к провайдеру, среднее число токенов на вызов, цена за тысячу токенов (null = «не сообщено»), доля вызовов, читавших кеш, и отдельно число вызовов, обслуженных локальным кешем.

Точки входа: `l1_outcome`/`contribution` в событиях завершения, `GET /api/models/usefulness`, карточка «Model usefulness» во вкладке Models, блок вклада под финальным ответом.

**Отклонения, о которых надо знать.** Вклад измеряется как **подтверждение ответа другими участниками**, а не как «влияние формулировку» — второе неизмеримо без выдуманных данных. И метрики пока показываются во вкладке Models; строка-подсказка в компактной панели выбора слева ещё не сделана.

Проверено: `tests/ModelMetricsTest.php` (17/0), `tests/ModelUsefulnessTest.php` (15/0), харнесс `tests/harness/models-tab.mjs` (406/0), `tests/ModelsTabDomTest.php` (7/0), `SmokeTest` 1534/54 без роста; живая проверка `/api/models/usefulness` на боевом (реальные медианы, хвосты, неответы с причинами).

**Проблема.** При выборе модели оператор видит идентификатор и семейство. Ни успешности, ни задержек,
ни цены, ни поведения в кеше рядом нет.

**Решение.** В каталоге и в списке выбора — по каждой модели: доля успешных ответов, задержка
(медиана и хвост), цена за тысячу токенов, попадания в кеш, участие в арбитраже. Данные брать из
журнала, а не из обещаний вендора.

**Затронуто.** `src/Models/*`, `src/Stats/*`, `assets/js/models.js`, `assets/js/model-selector.js`.

**Критерии приёмки.** Цифры соответствуют журналу за выбранный период; при малой выборке честно
сказано «данных мало».

**Риск.** Одна модель может выглядеть лучше из-за лёгких задач — сравнивать только внутри домена.

## R-11 — Надёжность вызовов модели

**Статус.** ✅ **Реализовано 23.09.2026.**

Что сделано:

1. **Таймаут на вызов модели** — `CallPolicy::timeoutSeconds()` (`pipeline.model_timeout_s`, по умолчанию
   180 с, зажат в 5…3600): медленный участник больше не держит весь веер до общего предела прогона.
2. **Повтор с бюджетом** — при **временных** отказах (таймаут, 429, 5xx, обрыв) модель получает
   `pipeline.model_retry_budget` дополнительных попыток; **постоянные** отказы (модель, которую провайдер
   больше не обслуживает; отказ по ключу; batch-only идентификатор) не повторяются вовсе — повтор там
   только тратит деньги. Классификация — `CallPolicy::classify()` по сообщению транспорта и HTTP-статусу;
   нераспознанный отказ считается постоянным.
3. **Размыкание в пределах прогона** — `ModelBreaker`: после `pipeline.breaker_failures` подряд идущих
   отказов модель перестаёт вызываться до конца прогона, поэтому мёртвый участник не переспрашивается в
   каждом цикле консенсуса. Состояние намеренно живёт в памяти одного прогона: это ответ на вопрос «стоит
   ли звать эту модель в *этом* совете», а не общесистемный health-check, и оно не превращается в
   устаревшее состояние — провайдер, который починился, будет опрошен в следующем прогоне.
4. **Честный итог** — `l1_outcome` в событиях завершения: сколько мнений пришло, кого не хватило и почему
   (вид отказа и причина), плюс список разомкнутых моделей с причиной. Информационно: терминальный вердикт
   сохраняет свои, более строгие правила, поэтому частичный совет по-прежнему считается ответом.
5. **Существующие ужесточения не ослаблены** — предполётная проверка и терминальный статус не тронуты;
   `SmokeTest` без роста состава падений.

**Отклонение от исходного описания, о котором надо знать.** Пункт «повтор с подменой на другую модель» я
не реализовал буквально: в ReVoAp каждый вызов L1 — это `role@model`, поэтому подмена модели меняет
**состав совета** — это не повтор, а подмена сущности, и она тихо изменила бы состав, который оператор
видел при отправке. Вместо этого отказ сообщается с классифицированной причиной, а в итоге видно, кого не
хватило. Если подмена нужна как **явный** выбор оператора («заменить выпавшую модель на эту»), это
отдельная задача: она требует подтверждения и записи в отчёт.

Проверено: `tests/ParallelChatDispatcherCurlFallbackTest.php` — 39/0 (было 29; +10 поведенческих проверок:
восстановление после временного отказа, отсутствие повтора при постоянном, размыкание и пропуск вызова в
следующем цикле, классификация отказов); `SmokeTest` 1534/54 без роста; остальные наборы без изменений.
Живая проверка: новые классы и ключи конфигурации на сервере, `code_state: current`, страница и

**Проблема.** Отказ одной модели в пуле заметно обесценивает прогон: иногда теряется весь веер, а
иногда ответ приходит с меньшим числом мнений без объяснения.

**Решение.** Свой таймаут на модель, повтор с подменой на допустимую замену при временных отказах,
размыкание на время для модели, которая стабильно падает, и честный итог: сколько мнений дошло и

**Затронуто.** `src/Connectors/ParallelChatDispatcher.php`, `src/Pipeline/PipelineEngine.php`,

**Критерии приёмки.** При отказе части моделей прогон завершается полезным ответом с перечислением

**Риск.** Повторы увеличивают расход — бюджет повторов должен быть ограничен.

## R-14 — Массовый сценарий на пакетном контуре

**Проблема.** Пакетный контур умеет один прогон, а его смысл — дешёвая асинхронная обработка **многих**

**Риск.** Пакет идёт долго — нужен понятный статус и уведомление (см. R-6).

- Данные для оценки: журнал шагов и ответов (`council_steps`, `council_model_responses`), статистика (`StatsCollector`, `SessionStats`, `TokenUsage`, `per_layer.cost/latency_ms/total_tokens`).

**Шаги.**

1. **Классификатор «неспешной» задачи (объяснимый, без магии).**
   Вход — уже имеющиеся сигналы: выбранный совет/скилл, число участников, история длительности и стоимости похожих прогонов, текущий режим. Выход — рекомендация «пакетом» или «синхронно» **с причиной текстом**. Правило живёт одной чистой функцией и покрывается тестом; никаких автопереключений — только рекомендация.

2. **Оценка экономии и времени до запуска.**
   Для кеша: из плана (`Planner`) известно, будет ли поставлена точка останова; из истории — фактическая доля попаданий по модели и домену; оценка — диапазон, подписанный как оценка. Для пакета: документированная разница в цене плюс ожидаемое время ожидания по истории. Показывается в карточке задачи рядом с составом и арбитром.

3. **Автоподбор политики кеша по измеренному результату.**
   Пороги и TTL берутся из документированных минимумов провайдера (уже в `Capabilities`), а дальше корректируются по факту: если за N прогонов попаданий нет, приложение предлагает выключить кеш для этой модели — у Anthropic запись стоит 1.25×, и платить её впустую нельзя. Предложение логируется; решение остаётся за оператором.

4. **Единая настройка «экономный режим»** — три уровня: `off` (как сейчас), `suggest` (рекомендовать и показывать оценку), `prefer` (включать пакет и кеш там, где это безопасно, оставляя переключатель). Настройка читается шагами 1–3 и видна в Settings и в карточке прогона.

5. **Учёт экономии** — одна строка на прогон и сводка за период: потрачено, сэкономлено кешем, сэкономлено пакетом. Это делает пользу режима измеримой и питает R-5.

6. **Проверки.** Чистые функции (классификатор, оценка, выбор политики) — модульными тестами со фикстурами истории; поведенческие — карточка показывает рекомендацию и оценку, переключатель уважается; приёмка: `off` возвращает сегодняшнее поведение **байт-в-байт** (это уже проверяется для кеша, тест сохранить).

**Критерии приёмки.** Для типовой задачи оператору видно предложение и ожидаемую экономию до запуска; после — фактические цифры; отказ от предложения не меняет поведение; настройка `off` полностью возвращает текущее поведение.

**Риски.** Пакет идёт до 24 часов — рекомендация не должна превращаться в самовольную задержку (поэтому уровень `suggest` по умолчанию). Оценка экономии неточна на новых моделях — подписывать как оценку. Кеш у недокументированных семейств не включать вовсе и не обещать (текущее правило сохранить).

**Оценка.** Шаги 1–2 — M, шаг 3 — S, шаги 4–5 — S–M, шаг 6 — постоянно. Итого первая очередь (1, 2, 4) ≈ M.
