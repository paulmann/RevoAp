1. What it is

RevoAp takes a natural-language query and routes it through a 4-layer LLM council pipeline, then shows the whole trail that produced the answer:

LayerDoes
L0 Skill routerPicks the skill that shapes the run (creating one when none fits).
L1 DistributionAsks every selected model, in parallel.
L2 NormalizationReshapes each answer into discrete claims. Internal — no LLM call.
L3 ConsensusScores agreement between the claims and flags conflicts.
L4 SynthesisWrites the final answer from the collected material.

Every step is recorded. The Chat panel renders the pipeline as it progresses (each card carries the model, tokens, latency, cost and, on a cache hit, the cache checksum), and the same data stays queryable afterwards:

  • Audit trail. Steps, per-model responses and pipeline events are persisted per session; History replays any past session end to end.
  • Model pool. The sidebar's Consensus models list selects which LLMs take part. Three or more gives a meaningfully richer consensus.
  • Skills and domains. Skills are declarative JSON definitions under src/Skills/definitions/; the consensus backends they select are listed by GET /api/consensus/skills (default semantic_consensus_reasoning).
  • Durable runs. A run started from the UI is a row in the revoap_jobs table, executed by the CLI worker outside PHP-FPM. Its lifecycle transitions land in revoap_job_events, which is what the History panel's job timeline renders.
  • External access. Runs can also be launched over the REST API (/v1/runs) or shared as read-only links.

2. Requirements

ComponentRequirement
PHP 8.5 CLI is the verified runtime; the source stays 8.4-compatible and composer.json requires php >=8.4.
Extensions pdo (plus the pdo_mysql driver for persistent storage), curl (connector HTTP and the parallel L1 dispatch), json, mbstring. pcntl is optional: with it the worker installs SIGTERM/SIGINT handlers and finishes the current cycle before exiting.
Database MySQL 8.0+ or MariaDB 10.6+. The job queue is acquired with SELECT … FOR UPDATE SKIP LOCKED; older servers fall back to a plain FOR UPDATE. The database itself is optional for a first look — without a DSN the app boots in memory mode, and History/Statistic have nothing to read.
Web server nginx or Apache in front of PHP-FPM. There is no api/ directory on disk: every URL is a virtual route dispatched by index.php, so requests that do not match a real file must be forwarded to it (the bundled .htaccess and nginx/revoap.com.conf do exactly that).
Writable paths logs/, cache/ and var/ must be writable by the account the web app and the worker run as (see Running the web app).

3. Configuration

Everything is driven by config.php at the project root plus a small number of optional override files next to it. Later layers win:

config.php               base tree shipped with the release
config/models/*.php      model catalogues expanded from the `model_files` key
.config.php              operator overlay — recursive leaf-merge of any section
.url                     scalar override of app.url
.sql.php                 full replace of the `database` block (emergency DB override)
var/config/runtime.json  values written by the admin Settings panel — merged last

Files you create

FilePurpose
config.phpBase configuration. Present in the release; edit it or overlay it (below).
.config.phpReturns a partial config tree (e.g. ['pipeline' => ['execution_mode' => 'legacy']]). Merged over the base tree; the recommended place for host-specific values, since it survives upgrades.
.{provider}.keyOne provider API key per file — e.g. .bothub.key, .openrouter.key, .openai.key. Create with umask 077 or chmod 600. The Settings panel writes these files for you when a key is saved.
.admin.keyThe admin token, 0600. Alternative to the REVOAP_ADMIN_TOKEN environment variable; either one unlocks every /api/settings/*, /api/logs/*, /api/security/*, /api/history/* and /api/statistics/* route.
var/config/runtime.jsonWritten by Settings. Merged on top of everything else, so a saved value takes effect on the next request without restarting PHP.

A file that fails to load never blocks boot: Config records what it found under app.diagnostics.config_sources and a human-readable summary under app.diagnostics.config_overrides, which /api/debug and the Settings diagnostics surface.

Optional feature flags

Each optional tab is enabled by a flag in config.php. The comparison is strict (=== true), so a truthy string does not enable anything, and the top-level spelling wins over the nested one when both are set:

return [
    'app' => [
        'SettingsTab' => true,
        'LogsTab'     => true,
        'SecurityTab' => false,
        'HistoryTab'  => false,
        'ApiTab'      => true,
    ],
    // Top-level aliases — the operator-friendly spelling.
    'SettingsTab' => true,
    'LogsTab'     => true,
];

When a flag is false the corresponding entry disappears from the sidebar and its endpoints answer 404 (for example settings_disabled / logs_disabled). The sidebar entry is not the gate — the flag and the admin token are — so hiding it means only that the feature is switched off.

The admin-key gate

Protect_Settings_by_Admin_Key decides whether the operator surface asks for the admin token at all. It is set in config.php and can be overridden per host in .config.php, which wins:

  • 1 — the token is required everywhere. This is the historical behaviour, and it is also what an absent setting means, so an install that has not opted out keeps the gate it always had. The token comes from .admin.key (or REVOAP_ADMIN_TOKEN), and the UI shows the unlock prompt.
  • 0 — no key is requested anywhere: the guards pass without one, the unlock prompt and every "admin token required" banner disappear, and nothing is reported as unauthorized. A banner under the header states that the surface is unprotected.

A 0 here is a deliberate hole, not a convenience. Anyone who can reach the host can then, with no credential at all, rewrite the provider API keys, the model catalogue and the consensus presets, change the database DSN, apply and baseline migrations and recreate the database, purge the response cache, read the log files, rewrite the IP allow/deny lists, read every stored session (the query, the full final answer and the prompts) and mint, rotate or revoke API keys. Use 0 only on a host nobody else can reach — behind .htaccess/HTTP auth, loopback-only, or on a private machine.

What the Settings panel changes

  • Providers / API keys — base URL, key and an active checkbox per provider. Save writes the key to .{provider}.key (0600), never into the JSON config. Test probes the live endpoint; Import models pulls the catalog.
  • Models — the active rows that drive consensus (bounded by models.catalog.max_rows, default 1000; see Model catalogue and Actualize).
  • Database — host, port, database, charset, socket, user, password, serialized into a DSN. Test opens a short-lived connection and runs SELECT 1.
  • Database maintenance — Check DB, Apply Migrations, per-file Apply, Baseline, Download schema dump, and ReCreate DB. See Database.
  • Runtime — app.debug, app.url, app.timezone, the model-response cache (enabled + TTL) and the pipeline switches parallel_l1 / max_roles_per_skill.
  • Cache — read-only statistics for the model-response cache plus bulk invalidation, so neither needs a shell.
  • Worker — worker status, the queue counts and a no-token self-test job.

Saved secrets are never echoed back: GET /api/settings returns a masked fingerprint and the source the key was loaded from (file / env / config).

The admin token gates write access to every secret RevoAp touches, so keep .admin.key (and any .{provider}.key) at 0600, owned by the account the app and the worker run as. Rotating it is a three-step job: generate a new value, replace the file or the environment variable, then let the 2-hour admin cookie expire or click Lock.

4. Database

db/schema.sql is the single source of truth. One import creates the complete schema — sessions, steps, model responses, events, the job queue (revoap_jobs, revoap_job_events), the memory store (memory_items), API keys, webhooks, the response cache and the bookkeeping tables:

mysql -u <user> -p <database> < db/schema.sql

Every statement is idempotent (CREATE TABLE IF NOT EXISTS), so re-importing it against a populated database is safe. The file declares its own versions — a top-of-file @schema-version and one @table-version <table> <semver> comment per table.

Settings → Database

  • Check DB compares the live database against db/schema.sql — tables, columns, types and NULL/NOT NULL — and adds a Schema versions section listing every table whose live version (recorded in app_config) differs from the declared one. Drift also raises the banner shown on every page.
  • ReCreate DB replays db/schema.sql and then baselines db/migrations/: each file is recorded as applied without being executed. That is safe because of the rule below.

Migrations

db/migrations/ holds the incremental migrations that converge an existing deployment on the current shape (014_memory_items, 015_api_keys, 016_webhooks, 017_worker_presence); the schema_migrations table tracks which of them have been applied. A fresh install needs none of them.

Two rules keep that consistent:

  1. Every table a migration creates is also declared in db/schema.sql. Otherwise a ReCreate DB would baseline the migration while the table was still missing.
  2. A migration exists only when an already-deployed database must converge without a full re-import. A change that only fresh installs need does not get one.

To change a table: edit its block in db/schema.sql, bump that table's @table-version and the file-level @schema-version, then — if existing installations must converge — add db/migrations/NNN_short_name.sql carrying the same annotation and idempotent DDL, and apply it through Settings. After a successful apply the declared versions are written into app_config, so a later Check DB comes back clean.

The model-response cache table also self-installs on first use (CREATE TABLE IF NOT EXISTS) when the database account may run DDL. Importing db/schema.sql remains the preferred path.

5. Running the web app

Point the web server at the project root, forward everything that is not a real file to index.php, and make sure PHP-FPM runs as an account that can write the three runtime directories:

PathWhy it must be writable
logs/ The debug log (logs/revoap-debug.log) and the always-on error log (logs/revoap-error.log) both resolve their directory here. If the directory cannot be created or written, logging degrades to silent — no warning, no line, nothing in the Logs tab. An empty Logs tab is almost always a permissions problem, not a quiet application.
cache/ The filesystem backend of the model-response cache writes cache/<provider>/<model>/<sha>.json. Without write permission that backend fails (and says so in the error log) while the database backend keeps working; with neither backend every run pays full price.
var/ Holds var/config/runtime.json (values saved in Settings) and the legacy flat cache tree var/cache/model-responses/.

The Security tab's self-check reports logs_dir_writable and var_dir_writable, which is the quickest way to confirm this from inside the app.

After a deploy

Reload PHP-FPM so the new sources are read (this resets OPcache), then hard-refresh the browser. Static assets are requested as ?v={asset_version}, where the token combines the app version with the newest mtime under assets/, so a re-deploy busts browser caches on its own. To confirm what the server is actually running, compare GET /api/debug → app.build_id with git rev-parse --short=12 HEAD.

Debug output

app.debug=true, GET /api/debug, or ?debug=1 on any URL all produce the same sanitized snapshot: database status and storage mode, discovered connectors with the reason each unavailable one was skipped, which active models point at a usable provider, the static stage plan, and actionable hints. API keys, DSN passwords and absolute paths are stripped before the payload is returned or logged.

6. Running the worker

Why it exists

A consensus run makes several slow, sequential LLM calls. When that ran inside the web request, an nginx or PHP-FPM timeout, an idle-database disconnect or a closed browser tab could abort it mid-flight. The worker is a long-lived CLI process that runs the same pipeline outside PHP-FPM and writes every pipeline event into the database; the browser simply replays those events, so a reload — even on another machine — rejoins the run instead of restarting it.

The queue is the revoap_jobs table. A job enqueued while no worker is running simply waits: start the worker later and it is picked up cleanly.

Command line

php bin/revoap-worker.php [--once|--loop] [--sleep=SEC] [--worker-id=ID] [--max-jobs=N] [--stale-after=SEC]
FlagEffect
--onceAcquire and run a single job, then exit. Default when no mode flag is given; safe for a foreground smoke check.
--loopDaemon mode: poll until SIGTERM.
--sleep=SECSeconds between empty-queue polls in --loop mode (default 1).
--worker-id=IDIdentifier written to revoap_jobs.locked_by (default <hostname>-<pid>).
--max-jobs=NStop after N successful acquires, even in --loop mode (default 0 = no cap).
--stale-after=SECHeartbeat threshold: running jobs whose heartbeat is older than SEC are reclaimed (default from config, 300).
--max-attempts=NOverride the recovery retry ceiling for this process (rows created with their own ceiling keep it).
--backoff-base=SECOverride backoff_base_seconds and rebuild the ramp as ×1 / ×4 / ×10 of it.
--backoff-max=SECCap the rebuilt ramp.
--no-auto-recoveryDisable auto-recovery: stale jobs are flipped to stale and stay there.
--statusPrint the worker diagnostic snapshot (the same JSON as /api/health/worker) and exit.
--helpPrint the usage text and exit.
 
# Drain the queue once and exit.
php bin/revoap-worker.php --once

# Daemon mode with a one-second tempo.
php bin/revoap-worker.php --loop --sleep=1 --stale-after=300

# Stable identifier for a named host, and a stop after ten jobs.
php bin/revoap-worker.php --loop --worker-id=worker-eu-1
php bin/revoap-worker.php --loop --max-jobs=10

# Diagnostic snapshot (exit code 0; the JSON carries the verdict).
php bin/revoap-worker.php --status
php bin/revoap-worker.php --help

Exit codes: 0 success — including "the queue was empty" in --once mode; 2 invoked from the web SAPI (the script refuses to run there); 3 help printed; 4 fatal bootstrap error (config missing, database unreachable).

Running it under systemd

Two unit templates ship in deploy/systemd/: revoap-worker.service for a single runner and revoap-worker@.service for a pool. Copy the one you need to /etc/systemd/system/, adjust user, group, working directory and PHP path, then:

# Single worker.
sudo cp deploy/systemd/revoap-worker.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now revoap-worker.service
sudo systemctl status revoap-worker.service
sudo journalctl -u revoap-worker.service -f -o cat | jq .

# Pool: one process per instance (revoap-worker@1, @2, …).
sudo cp deploy/systemd/revoap-worker@.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now revoap-worker@1 revoap-worker@2
sudo systemctl status 'revoap-worker@*'
sudo journalctl -u 'revoap-worker@*' -f -o cat | jq .

Each instantiated unit pins --worker-id=worker-%i, so /api/health/worker lists stable identifiers (worker-1, worker-2, …) instead of hostname-pid pairs. The units restart on any non-zero exit (Restart=always, RestartSec=5), allow 600 s for a graceful stop, and emit one JSON line per event to journald.

Run the worker as the same account the PHP-FPM pool runs as (the templates ship User=www-data). That keeps logs/, cache/ and var/ writable for it, and it keeps the 0600 secret files (.admin.key, .{provider}.key) readable by the process that needs them. A worker under a different account usually dies at bootstrap with exit code 4 and a worker.bootstrap.* line.

Tempo and recovery

  • --sleep (environment WORKER_SLEEP) is how long an idle worker waits between queue polls — one SELECT per interval per process. 1 suits interactive hours; 5 is the recommended quiet-hours setting. A non-empty queue does not sleep: jobs run back to back.
  • --stale-after (environment WORKER_STALE_AFTER) is the heartbeat age at which a running job is considered abandoned. The sweep runs before every acquire — so raising --sleep also postpones the worst-case recovery by the same amount.
  • Retries. Auto-recovery is on by default: a stale job is requeued with its attempt counter incremented and a next_run_at in the future (the backoff), and acquireNext() skips rows that are not due yet. When the retry budget (max_attempts, default 3) is exhausted the job becomes failed with exhausted_retries in its error envelope. Ramp and limits come from pipeline.jobs.recovery.* (auto_recovery_enabled, max_attempts, stale_after_seconds, backoff_base_seconds, backoff_max_seconds), whose leaves are clamped on read.

worker.env

deploy/systemd/worker.env.example is the template for the unit's EnvironmentFile — copy it to /etc/revoap/worker.env, keep it 0640 and never commit it. It carries WORKER_SLEEP, WORKER_STALE_AFTER, WORKER_MAX_JOBS, WORKER_BACKOFF_BASE, WORKER_BACKOFF_MAX, WORKER_MAX_ATTEMPTS and, if the host needs one, an env-provided REVOAP_ADMIN_TOKEN. Values there override the inline defaults in the unit, which is how the tempo is tuned without editing unit files.

How much parallelism?

A worker handles one job at a time: it acquires a single row, runs it to a terminal state, then polls again. Parallelism therefore equals the number of worker processes, which is why the pool template exists. Two workers can never take the same job — the row is claimed inside a transaction and fenced by the row lock.

Size the pool from measurements rather than guesses: workers ≈ peak queue length ÷ mean job duration. Start with one or two instances, watch /api/health/worker, and measure real per-process memory (systemctl show revoap-worker@1 -p MemoryCurrent) before setting a hard limit such as MemoryMax — an unmeasured cap can kill a worker in the middle of a long pipeline.

The worker also upserts a presence row (revoap_worker_presence, throttled to once per second) while it runs and removes it on a clean exit, so an operator can tell "alive and idle" from "never started" and from "crashed".

7. Operations & troubleshooting

Start with GET /api/health/worker (public) or php bin/revoap-worker.php --status: both emit the same envelope, whose worker_status field is the fastest verdict.

worker_statusMeansDo
not_runningJobs are queued but no worker heartbeat is recorded and no worker process is alive.Start the worker — systemd, or --once for a single drain.
migration_missingThe revoap_jobs table does not exist.Import db/schema.sql, or Settings → Database → ReCreate DB.
staleThe newest heartbeat is older than the stale threshold.Check the journal and restart the worker — the previous process stopped without cleaning up.
healthyWork is in flight, or jobs are queued with a live worker picking them up.Nothing.
idleNo queued or running jobs.Nothing.
unknownFallback — the snapshot could not be classified.Re-read; check the application logs.

If pipeline.execution_mode is legacy, the envelope does not report a status of its own for it: the recommendations list carries the instruction to set it back to job (in .config.php or var/config/runtime.json), and the status stays derived from the queue and heartbeat as in the table above.

Symptom by symptom

  • A job stays queued and the chat shows no events. Either no worker is running, or the job is inside an auto-recovery backoff window (next_run_at in the future). The commands block of /api/health/worker carries the exact start/restart commands for the host.
  • The worker died mid-run. The row is reclaimed as stale and requeued with a backoff until the retry budget runs out; the History panel's job timeline shows stale.detected → stale.requeued, and on exhaustion stale.exhausted plus a failed status carrying exhausted_retries. The worker's own log lines are worker.stale.requeued, worker.stale.exhausted and worker.reclaim.stale.
  • Logs are empty. logs/ is not writable by the account the app runs as, so logging silently degrades. Confirm with the Security self-check (logs_dir_writable) and the Logs tab, which lists each file with its writable flag.
  • The response cache never hits. Look for cache.fs_store.mkdir_failed or cache.fs_store.write_failed (cache/ not writable) and cache db store failed (database backend write failure) in logs/revoap-error.log. A cache.store.refused line is not a permissions problem: it records that a response was deliberately not cached because it was empty or an error envelope. Settings → Cache shows entries, bytes and the hit counter — note the counter exists only for the database backend.
  • Cross-session memory stopped working. A memory.repo.table_missing warning means memory_items is absent, so the memory stack degrades to "no memory" instead of failing. Its hint names the fix: Settings → Database → ReCreate DB, or re-apply db/migrations/014_memory_items.sql with the per-file Apply button. Memory is only in play at all when pipeline.memory_top_k is greater than 0.
  • The chat stays on "no events yet" although the job finished. A worker.job.session_mismatch warning means the engine ran under a different session id than the job row expects, so the replay endpoint has nothing to stream for that session — the note in the log line says exactly that.
  • A model call returns HTTP 404. Retired model ids are the usual cause; the resulting L1_FAILED event carries a hint pointing at the provider's /models endpoint so the id can be corrected in the model list. A MODEL_NOT_FOUND for an id ending in :batch is a different case — such a model is served only through the Batch API (see Batch mode and :batch models), which the engine now refuses up front rather than at the end of a run.
  • "MySQL server has gone away" (driver codes 2006 / 2013). The database wrapper detects the dropped connection, reconnects and re-runs the statement once. To make it rarer, raise wait_timeout for the application user and keep pipeline.parallel_l1 enabled so L1 calls overlap instead of serializing.
  • A schema-drift banner appears on every page. A table's live version in app_config differs from the @table-version in db/schema.sql. Apply the pending migrations in Settings → Database.
  • analyzer.* warnings. The request analyzer could not use its live path — analyzer.chat_failed, analyzer.connector_missing, analyzer.connector_lookup_failed, analyzer.response_truncated, analyzer.json_unparsable — and fell back to its heuristic envelope. Runs continue; fix it if the analyzer's provider or model is misconfigured.
  • worker.bootstrap.* lines. The worker could not boot: worker.bootstrap.config_failed (config missing or invalid), worker.bootstrap.no_database (no DSN or the database is unreachable), worker.bootstrap.skill_seed_failed (skill seeding failed — not fatal), or worker.bootstrap.exception. The fatal ones exit with code 4, and systemd restarts the unit after RestartSec.

10. Batch mode and :batch models

Some Bothub models are served only through the provider's asynchronous Batch API, and their identifiers carry a :batch suffix (for example gpt-5.6:batch). A batch call is not an ordinary call that happens to be slow: the provider accepts a file of requests, works through it in the background and hands back a file of answers, so there is no synchronous response to wait for.

The suffix is therefore a mode, not part of the model's name. x and x:batch are one line and one family — the version and family comparisons treat them as the same model — and each list marks the batch form so it is not mistaken for its synchronous twin.

  • In a normal (synchronous) run, a :batch id is refused before any model is called, with the reason stated. The model pool in the composer refuses it too. Earlier the identifier was accepted, reached the provider, and surfaced as a 404 MODEL_NOT_FOUND at the end of a run that had already paid for every other layer.
  • In batch mode a :batch id is exactly what the run is for, and both the plain id and its batch form are offered.

Running a batch from Chat

  1. Tick Run via Batch API in the composer. The toggle is disabled with a stated reason when the deployment is not ready for it — no Bothub key, or the batch surface could not be resolved.
  2. Send the query. Only the L1 fan-out is batched: every L1 call becomes one line of the uploaded JSONL file, keyed by a deterministic custom_id. L2, L3 and L4 depend on the L1 answers, so they run normally as soon as the results arrive — the consensus itself is not batched.
  3. Watch the composer's batch card: the phase, the provider's status, how many requests went out, how long ago, the 24-hour completion window, and how many rows failed or came back with no answer. Cancel batch asks the provider to stop; the request is delivered on the next worker pickup, and the run only becomes cancelled once the provider has actually been told.

The worker never blocks while a batch is outstanding: the job parks itself on next_run_at and wakes up for the poll, so the queue keeps draining. Polls are 30 seconds apart for batches of up to 1000 rows and 150 seconds above that, which is the provider's own sizing rule. The batch state is persisted with the job, so an outstanding batch survives a worker restart.

A run waiting on the provider is neither finished nor failed. History shows it as awaiting batch, with the same readout as the Chat card, instead of as a running row that looks stalled.

Partial failures

Row outcomes are kept separately. A line the provider rejected carries its own status_code and body; a request that came back with no answer at all is reported as missing rather than silently dropped. Rows are matched by custom_id and never by position, so a provider that reorders its output file changes nothing. A batch in which some rows failed still feeds the consensus with the rows that did succeed, and the counts are shown in the card.

Which models can be batched

The list of batch-capable models is the provider's own answer (GET /api/council/batch/models, backed by the provider's GET /batches/models), not a list shipped with the app. The answer is three-valued — batch-capable, not batch-capable, or unknown — and unknown only ever means "the provider could not be asked", never "this model does not support it". When the capability call is unavailable the composer says so, and no model is hidden on the strength of a guess.

11. Prompt caching

A consensus run asks the same models the same base-file + profile + role prompt again and again: every role in the L1 fan-out shares one long, unchanged prefix, and paying full input price for that prefix on every call is the largest avoidable cost of a run. Prompt caching lets the provider keep that prefix and bill the repeat as a cheap read. RevoAp enables it where the provider documents it and surfaces the figures the provider returns.

This is the provider-side prefix cache, not the response cache. The response cache (Settings → Cache) stores finished answers in RevoAp and skips the network call entirely; prompt caching changes what the provider charges for a call it still performs. They are switched on and off separately.

Who caches, and how

For the explicit families the breakpoint goes on the last stable message of the prefix — the end of the system block, not the end of the request — so the dynamic part of the prompt (the query, and any memory recall) stays outside the cached region. Raising prompt_cache.max_breakpoints moves it further back through the system messages, up to the documented ceiling of four. A prefix shorter than the size guard gets no breakpoint at all, because caching below the provider's documented minimum would cost a round trip and save nothing; the guard is raised to a family's minimum and never lowered.

How long it lives, and what it costs

The cache lives 5 minutes by default, or 1 hour if you choose it (prompt_cache.ttl, either 5m or 1h; anything else is coerced back to 5m). A one-hour entry is written at the provider's own premium on the families that charge for writes. Bothub is the only connector that documents a caching surface, so requests to every other provider keep the payload they had before, byte for byte.

Turning it on and off

Settings → Prompt caching carries the switch, the TTL, the breakpoint count and the size guard, and renders the same capability table the request builder reads, so the card cannot drift from the behaviour. It saves through POST /api/settings/prompt-cache, and an undocumented TTL is refused rather than quietly coerced. The master switch is prompt_cache.enabled: setting it to false in config.php or .config.php turns the whole feature off in one step and restores the legacy request body exactly.

Reading the statistics

  • Chat shows the cache figures per step and per run, History per run and per stage, and the Statistics page rolls a run up. The figures are the tokens read from the cache, the tokens written to it, and the saving the provider reports through cache_discount.
  • A missing figure is not a miss. A provider that reports nothing about caching leaves the values empty, and the UI renders "no cache data" rather than a zero — a zero would read as "the cache was consulted and did not help", which is a different fact and often a false one.
  • No statistics at all usually means the provider returned no usage block. Check that the family is listed as caching above, that the prompt prefix clears that family's minimum size, and that the model belongs to the family you expect.

12. Model catalogue and Actualize

The catalogue is every model RevoAp knows about; the pool is the subset a run actually calls. Actualize (Models tab) reconciles the two against what the provider really serves.

What Actualize does

  1. Import models (importing_models) — fetch the provider's live list from the chosen source (bothub or openrouter) and merge it into the catalogue. This runs in the worker and comes first, because every later stage reasons about the list it produces. The report names what was fetched, added, already present and discarded, and a failed import fails the run loudly instead of continuing on the previous list.
  2. Analysing models (analysing_models) — ask the analyzer model which models should take which role.
  3. Assigning models to consensuses (assigning_presets) — write the consensus presets and the linked roles.
  4. Result (finish) — publish the verdict, or fail on the stage that died.

The run is all-or-nothing: a snapshot of the pre-run state is written before anything is changed.

The catalogue ceiling

A provider can serve more models than a list can usefully hold. models.catalog.max_rows (in config.php or .config.php) sets the ceiling — default 1000, and 0 for no ceiling at all. It is applied once, when the catalogue is persisted and merged, and it is not a blunt cut: rows the pool, a preset or a linked role refers to are never discarded, and the rest are ranked as "newest release in its family", interleaved across families so one prolific provider cannot fill the list by itself. A model the provider no longer serves is marked inactive (stale) with the reason, rather than kept and offered silently.

The ceiling is a real constraint, not a cosmetic one. The pool, the presets and the linked roles must all be active catalogue rows: a run that cannot satisfy that fails, rather than reporting success with nothing to call. When a ceiling is genuinely too low for the pool the run's own repair pass says which entries it removed and why.

Which model runs the assignment

Actualize uses its own model, models.actualize.analyzer, chosen on the Actualize card. When it is not set the section inherits analyzer.provider / analyzer.model and says that it did — it never writes them. The separation matters: analyzer.* classifies every incoming query for the L0 router, so pointing Actualize at a stronger (or cheaper) model must not silently re-point the classifier.

When it fails

A failed run is reported as an error, on the stage it died in, and the card names the run it is describing (job id and times) so a verdict can never be attributed to the wrong run. Pressing Actualize again clears the previous verdict immediately, instead of leaving the last run's green stages on screen while the worker starts the new one.

Rolling back

Roll back to the last snapshot restores the state saved before the last run — the catalogue rows, every preset definition and the model pool the sidebar reported — in one step. There is one snapshot, and it belongs to the last run: rolling back after a second actualization restores that second run's starting point, not the first one's.

13. System health

Settings — System health is one screen for the failure classes that used to be found by hand: the worker running older code than what is deployed, a migration that was never applied, write permissions that broke, a stale model catalogue, a pool that drifted out of the active catalogue, a database connection that was lost. Each check says what is wrong and offers the button that answers it.

What is checked

  • Worker code version — the version the running worker loaded against the code on disk (code_state). A PHP process keeps the classes it loaded at start-up, so a worker started before a deploy runs the old code with no syntax error anywhere.
  • Migrations and schema version — pending migration files, and the version recorded in the database against the one db/schema.sql declares.
  • Writable directories — var/config, runtime, cache and logs, with the mode, the owner and the user the PHP process runs as.
  • Model catalogue freshness — how many rows are active and when the catalogue was last actualized.
  • Pool and roles inside the active catalogue — every row the pool, the domain presets and the three linked roles name has to exist among the active catalogue rows.
  • Database connections — whether a handle is held right now, and how many times the connection was lost.

How a repair works

Every repair is one of the endpoints the Settings cards already use (POST /api/settings/migrations/apply, POST /api/worker/restart, POST /api/models/actualize). It asks for confirmation first, runs behind the admin gate, is idempotent and is written to the log. Afterwards the panel reads the state again and prints the fresh verdict for that check (State re-read at …) — so "fixed" is something you can see, not something the panel claims. With the admin gate closed the server's refusal is shown verbatim (Refused (HTTP 401): admin token required); the panel never reports a repair it did not make.

What the panel will not do

Anything that lives outside the application is reported as a command and never executed: chown / chmod for a directory the PHP user cannot write, and systemctl for a service that has to be restarted. The panel needs no root and no sudo, and it never runs a shell command built from request data.

First-run checklist

A fresh installation also gets a compact checklist — admin key, DSN, schema, provider keys, catalogue, worker, writable directories — collapsed under the checks. It is read from a public endpoint, so it is available on the locked screen as well, before the admin token is entered.
